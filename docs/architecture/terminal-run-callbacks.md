# Terminal run callback handling

A benchmark run has one execution outcome. QUEUED/RUNNING may accept any existing terminal callback status. The first committed terminal callback is authoritative; later valid terminal callbacks, whether identical or contradictory, return normally without rewriting run timestamps/host/failure, metrics or artifacts. This extends the existing rule that a late start cannot reopen a terminal run to its result payload. It does not introduce a correction operation or new HTTP status. Clients still receive 400 for a nonterminal result status and 404 for a missing run; controller authentication/validation is unchanged.

This choice preserves the worker's existing 2xx acknowledgement behavior for retries while preventing a delayed failed/succeeded result or same-status changed payload from replacing a completed result. There is no supported terminal-to-terminal correction workflow in this API. Do not use replay as an administrative correction tool. Existing terminal rows missing metrics/artifacts are not repaired automatically by a retry; investigate those records rather than silently mutating a completed run.

Both start and result resolve the run with a PESSIMISTIC_WRITE query inside the existing service transaction. Concurrent mutations of the same row must serialize: the later transaction observes the terminal state after the earlier one commits. Run, metric and artifact writes remain in that one transaction; an unchecked persistence failure rolls the transaction back, allowing a later delivery to perform the first completion. No HTTP call or benchmark computation is added under the lock. Lock wait/timeout/deadlock failures may propagate for retry, rather than acknowledge a completion that did not commit.

The unit regressions use real service methods, deterministic Instant.now fixtures, repository mocks and a real Spring transaction proxy with an in-memory rollback resource. They cover first results, all terminal statuses, exact/changed/contradictory retries, late starts, active starts, invalid result status, missing runs and persistence failure/retry. They do not establish actual PostgreSQL lock behavior, database rollback or RabbitMQ acknowledgement. Repository lock metadata and service transaction annotation are checked; real two-connection PostgreSQL concurrency and rollback tests remain deployment validation work. Other writers bypassing the service are outside this serialization guarantee.

This change prevents duplicate API completion effects after a result has committed; it does not provide exactly-once execution/delivery. The worker journal's pre-persistence crash window, retained-history expiry, single-worker assumptions and API-to-broker publication gap remain. No outbox, migration, dependency, route, security or public DTO change is included.

## Opt-in PostgreSQL concurrency gate (NOT RUN)

`TerminalRunCallbackConcurrencyIT` uses the existing `@IntegrationTest`/EmbeddedSQL PostgreSQL infrastructure, two real TransactionTemplate transactions and the real service proxy. It holds the first result transaction open, then observes the second backend in pg_stat_activity waiting on a lock for result/result and result/start. It releases the first commit and checks the authoritative status/metric and one artifact. Only its own seeded IDs are deleted. No H2 substitute.

On an explicitly disposable environment with required existing infrastructure available, opt in for example in PowerShell: `$env:BENCHLAB_TEST_CALLBACK_CONCURRENCY='true'`, then `./mvnw.cmd -o '-Dit.test=TerminalRunCallbackConcurrencyIT' verify`; restore/remove the environment variable afterwards. The test is disabled without that flag. This command may invoke other unit tests and the existing container infrastructure. Do not run against production or start/configure host services to bypass missing prerequisites. Here only `./mvnw.cmd -o -DskipTests -DskipITs test-compile` passed after adding the opt-in test; its PostgreSQL race cases are NOT RUN. Review exact test and container fixture behavior before execution (the existing PostgreSQL fixture enables container reuse).
