# Reviewed backend/worker release

The PR runs the real PostgreSQL callback race and injected artifact-write rollback/retry tests, Linux Go/helper tests, and a dedicated ephemeral Docker-in-Docker worker/API/RabbitMQ recovery scenario. The latter replaces a killed worker retaining its journal volume, verifies redelivery without recalculation, retries an accepted callback after response loss, exercises 12,000 bytes of user stderr through the Linux helper, and restores a fresh fixture database dump into another disposable database. No production endpoint is used. A failed/skipped/unstarted gate does not authorize promotion.

GitHub-hosted ubuntu-24.04 is disposable. The gate job has a 45-minute timeout and the scenario a 25-minute timeout; all fixture services have CPU/memory/PID limits and nested Docker storage is a 2-GiB tmpfs. Outer builds/images/cache still use runner disk; preflight requires 15 GB free and reports runtime capacity. This is not a claim of an absolute disk quota or secure privileged-container isolation. No fixture is allowed on the production host. Resource exhaustion is failure, never a skipped gate.

Production uses the existing prod environment and manual dispatch only. Before dispatch resolve missing VPS_HOST/VPS_USER variables, validate the confirmed /opt/benchlab/app target, and record the exact merged SHA and resolved GHCR digests of API and worker built from that SHA. No remote settings are changed by this PR. The deployment template keeps the worker_results named volume across container replacement. Never use down -v or delete pending journals during release or rollback. Historical checksums have older prefix semantics; journal replay preserves their payloads unchanged.

The current workflow has no automatic rollback and uses SHA tags, not digest-pinned promotion. This PR only fixes quiet Compose validation and validates target/exact source SHA before SSH writes; it does not claim to have deployed hardened promotion. A release operator must retain the prior .env and Compose plus API/worker image digests, confirm tag resolution immediately before promotion, serialize the operation (no concurrent dispatch), and stop if a tag resolves to an unexpected digest. Preserve the existing web image/revision unless a separately reviewed promotion explicitly includes rebuilding unchanged web source; this workflow currently builds all three images. No frontend source is changed here.

Before rollout take a checked production PostgreSQL backup using the actual inspected container identity; do not rely on the old backup script's default container name. Keep the backup outside the synced app/deploy directory with private permissions, verify pg_dump exit/nonempty output, and restore into an isolated PostgreSQL instance matching production to check Liquibase metadata and application row counts. The fixture restore gate proves the backup format/procedure with synthetic data, not the existence or restorability of a fresh production backup. No new database migration is introduced by the reviewed delta; still compare deployed Liquibase history before release.

Rollback must restore compatible API+worker images and required environment/Compose without deleting database/journal volumes. Drain current worker callbacks and stop admission before downgrading to an older worker lacking journal recovery; if pending entries remain, do not start an old worker that would recalculate them. Existing admin-password startup behavior and secrets must remain matched to the environment. An API health pass alone is insufficient: inspect worker readiness, image revisions, journal/backlog and a separately authorized synthetic end-to-end smoke. Health/readiness failure or corrupted result behavior stops rollout and triggers the reviewed image rollback path; database restore is a separate decision, not an automatic response to application failure.
